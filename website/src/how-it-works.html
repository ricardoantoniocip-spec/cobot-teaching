How it works

The operator shows. The software writes. An engineer approves.

Five steps take a task from a video to a robot program. The AI only names what it sees. The numbers come from measurement, and the robot code comes from a fixed generator that gives the same program for the same input, every time.

Take 1, start to finish: webcam video, AI step labels, task file, URScript on a simulated UR5e, and the same task on the SO-101 digital twin. 52 seconds, no sound.

01

Record

An operator does the task once, at normal speed, in front of an ordinary webcam. No markers, gloves or special suit are needed for the first version.

  • One take is enough for simple pick-and-place
  • The person who does the job every day is the teacher
02

Track

Computer vision follows the shoulder, elbow, wrist and fingers frame by frame. Grasp and release are found from when the object starts and stops moving, which is more reliable than guessing from hand shape.

# measured from the video, millimetres
reach     t 0.0 – 3.1 s
grasp     t 3.1 s         at  176.3,  46.1
move      t 3.1 – 8.5 s
release   t 8.5 s         at  222.7, -72.9
retreat   t 8.5 – 9.5 s
03

Label

A vision language model looks at key frames and names each step, the object and the places involved. It also flags what a robot needs to watch out for.

It writes words, not numbers and not robot code.

# written by the vision AI
grasp    "grip the carton near its top with the whole hand"
release  "let go of the carton standing on the seat"

# review notes for the engineer
"the seat cushion is soft: a robot placing here
 needs a slower release"
04

Generate

Positions and labels are combined into a small task file: objects, locations and skills such as pick, place, wait for a signal and repeat. It describes what to do, for any robot brand.

A fixed generator turns the task file into the robot's native program, with comments an engineer can follow. To change the task you change the task file and generate again.

task file 
"steps": [
  {"do": "home"},
  {"do": "pick",  "object": "juice_carton", "at": "armrest"},
  {"do": "place", "object": "juice_carton", "at": "sofa_seat"},
  {"do": "home"}
]
URScript · Universal Robots 
# step 2/4: pick juice_carton at armrest
movej(get_inverse_kin(pose_trans(loc_armrest,
      p[0, 0, -0.07, 0, 0, 0]), qnear=home_q))
movel(pose_trans(loc_armrest, p[0, 0, -0.02, 0, 0, 0]),
      a=0.8, v=0.15)  # down to grasp height
ct_gripper(True, 0.5)  # close gripper
05

Verify

Every program runs in simulation before a real robot moves. For UR cobots that is URSim, the official offline simulator, where each step is checked against the task file. A digital twin of the SO-101 research arm replays the same task.

Programs are marked NOT APPROVED until an engineer has run them in simulation and then on the robot at reduced speed.

Why it is built this way

AI where it helps. Fixed rules where it matters.

Predictable

Same input, same program

The AI never writes free-form robot code. A deterministic generator does, so results can be checked and repeated.

Readable

Native code, your controller

The output is the robot's own language with step comments, ready to open, review and adjust on the teach pendant.

Safe by process

An engineer stays in charge

Simulation first, then reduced speed with an engineer present. The cell's risk assessment stays with the integrator, as it should.
